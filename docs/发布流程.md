# 发布流程

版本号遵循语义化版本，唯一来源是 `package.json` 的 `version`（`dshenv --version` 读取它）。推送 `v<版本>` tag 后，`.github/workflows/release.yml` 自动完成发布。

## 步骤

1. 发布改动通过 PR 合入 `master`（`master` 受保护：必须走 PR，`check (22)`、`check (24)`、`e2e` 通过后才能合入），确认 `master` 上 CI 通过，本地切到最新的 `master` 且工作区干净。
2. 修改 `package.json` 的 `version`。
3. 在 `CHANGELOG.md` 顶部新增 `## <版本> - <YYYY-MM-DD>` 小节，写明新增、变更与修复。
4. 把 `README.md` 与 `docs/使用教程.md` 安装说明中的版本号（`@costa92/dshenv@<版本>` 与 `#v<版本>`）、`docs/examples/github-actions/dshenv-check.yml` 的 `DSHENV_VERSION` 改为新版本（`docs/examples/container/README.md` 用 `v<版本>` 占位，不必改）。
5. 本地检查：

   ```bash
   pnpm typecheck && pnpm test && pnpm build
   node bin/dshenv.js --version   # 应输出新版本
   ```

6. 版本提交同样走 PR，合入后在 `master` 上打 tag：

   ```bash
   git switch -c release/v<版本>
   git commit -am "chore: release v<版本>"
   git push -u origin release/v<版本>
   gh pr create --fill && gh pr merge --merge --auto   # CI 通过后自动合入
   git switch master && git pull --ff-only
   git tag -a v<版本> -m "v<版本>"
   git push origin v<版本>
   ```

## Release 工作流做什么

1. tag 必须等于 `v` + `package.json` 的版本，且指向 `master` 上的提交（`master` 只接受经过检查的 PR），否则失败。
2. 从 `CHANGELOG.md` 取出该版本小节作为 Release 说明，缺少该小节则失败。
3. 与 CI 相同的 `typecheck`、`test`、`build`。
4. `pnpm pack` 生成 `costa92-dshenv-<版本>.tgz`，在临时目录里 `npm install` 这份文件，确认 `dshenv --version` 输出该版本、`dshenv --help` 能运行。包内已含 `lib/`，安装时不需要构建。
5. `publish` job 只下载上一步的这份文件，把 npm 升级到固定的 11.x 版本，通过 Trusted Publishing 发布到 npm（`@costa92/dshenv`，公开，自动附带 provenance），再创建 GitHub Release 并附上同一文件。

前 4 步在 `build` job 里执行，只有读仓库的权限，checkout 也不保留凭据；发布需要的 `id-token: write` 和创建 Release 需要的 `contents: write` 只给 `publish` job，它不 checkout、不安装依赖、不跑任何项目脚本。工作流里的 action 都固定到 commit SHA（注释里写着对应版本），升级时连同 SHA 一起改。

任一步失败都不会创建 Release。修正后删除远端 tag（`git push origin :refs/tags/v<版本>`）与本地 tag，重新打 tag 推送。

例外：npm 已经发布成功、只有最后的 `gh release create` 失败时，不要重推 tag，npm 不允许再次发布同一版本，重跑会在发布步骤失败。直接手动创建 Release，附上 npm 上的同一份包：

```bash
npm pack @costa92/dshenv@<版本>
awk -v v="<版本>" '/^## /{f = ($2 == v); next} f' CHANGELOG.md > release-notes.md
gh release create v<版本> costa92-dshenv-<版本>.tgz --title v<版本> --notes-file release-notes.md
```

## npm Trusted Publishing

发布优先走 Trusted Publishing：npm 通过 GitHub Actions 的 OIDC 身份信任 `release.yml`，不需要 token，并自动生成 provenance。要求 npm CLI ≥ 11.5.1、Node ≥ 22.14.0（工作流会先升级 npm）、`publish` job 的权限 `id-token: write`。

`NPM_TOKEN` 是备用：`publish-oidc` 步骤不带 token 发布，失败时 `publish-token` 步骤带上仓库 Secret `NPM_TOKEN` 重发（同样生成 provenance），并在运行页留下一条 warning「npm trusted publishing failed; publishing with NPM_TOKEN instead」。看到这条 warning 就去 `publish-oidc` 的日志里找 `npm verbose oidc` 开头的一行，那是失败原因。

### 检查两种发布方式（不发布）

在 Actions 页面手动运行 Release 工作流（或 `gh workflow run release.yml --ref master`）。它跑完质量检查、打包和安装检查后，在 `publish` job 里：

- `check-oidc`：`npm publish --dry-run --force` 走一遍 OIDC 换取凭证，日志里没有 `oidc Successfully retrieved and set token` 就失败，并在 error 里写出 npm 给的原因；`--dry-run` 不上传任何东西，`--force` 只是跳过「版本已发布」的检查。
- `check-token`：用 `NPM_TOKEN` 执行 `npm whoami`，确认备用 token 仍然有效（Granular Access Token 最长 90 天有效）。

手动运行不会校验 tag、不会发布到 npm，也不会创建 GitHub Release。

### 一次性配置

需要包的维护者登录 npmjs.com 操作：

1. 打开 `@costa92/dshenv` 的 **Settings → Trusted Publisher**，选择 GitHub Actions，填写：Organization or user `costa92`，Repository `dshenv`，Workflow filename `release.yml`，Environment 留空。
2. 保留 `NPM_TOKEN` 作为备用时，**Publishing access** 不能选「disallow tokens」，否则备用 token 无法发布；token 过期前在 npmjs.com 重新生成并更新仓库 Secret。以后不再需要备用时，再选「Require two-factor authentication and disallow tokens」，删除 `publish-token`、`check-token` 两个步骤和仓库 Secret（`gh secret delete NPM_TOKEN -R costa92/dshenv --app actions`），并撤销 token。

`check-oidc` 报 `package not found` 或发布 404 时，先检查上面四个字段是否与仓库、工作流文件名完全一致，以及是否已保存。

包名用 `@costa92` 作用域：npm 以「与 dotenv、osenv 过于相似」为由拒绝了无作用域的 `dshenv`。
