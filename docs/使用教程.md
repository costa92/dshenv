# dshenv 使用教程

`dshenv`（npm 包 `@costa92/dshenv`）用于以声明式清单管理 DeepSeek Harness（DSH）的 Profile 插件。它会比较“清单中的期望状态”和“Profile 中的实际状态”，生成计划，并在当前支持范围内调用 DSH CLI 完成安装或更新。

> 当前能力边界：真实环境变更支持 `install`、`update`、`enable`、`disable`、受管 `remove` 和 `configure`。`configure` 写入 Profile `cordis.patch.yml` 的 `# dshenv:begin/end` 块。`purge` 把有所有权的受管 patch 移入 `envctl/trash`，不删除外部源码。

## 1. 前置条件

- Node.js `^22.19.0` 或 `>=24`
- pnpm
- 一个可用的 DSH CLI，或者本地 DeepSeek Harness 源码目录

在项目目录安装依赖并构建：

```bash
cd "$HOME/code/dsh/dshenv"
pnpm install
pnpm build
```

开发期间也可以使用 Makefile：

```bash
make install
make build
make check
```

## 2. 安装为全局命令

从 npm 安装（推荐）：

```bash
npm install -g @costa92/dshenv
# 或
pnpm add -g @costa92/dshenv
dshenv --version
```

npm 包已含构建好的 `lib/`，安装时不需要构建；固定版本用 `@costa92/dshenv@0.9.0`。各版本见 [Releases](https://github.com/costa92/dshenv/releases)（附同一份 `.tgz`），变更见 [CHANGELOG](CHANGELOG.md)。

也可以从 Git 地址安装指定 tag：

```bash
pnpm add -g --allow-build=@costa92/dshenv "git+https://github.com/costa92/dshenv.git#v0.9.0"
```

`#` 后可换成其他 tag、commit 或 `master`（未发布的最新代码）。安装时 pnpm 会在克隆中执行 `prepare` 构建 `lib/`；pnpm 10 默认不运行依赖的构建脚本，所以必须带 `--allow-build=@costa92/dshenv`，否则安装后缺少 `lib/` 无法运行。npm 从 Git 地址安装时会在准备阶段崩溃（npm 10.9 arborist 缺陷），请使用 pnpm。

开发者从当前源码目录建立全局链接：

```bash
cd "$HOME/code/dsh/dshenv"
pnpm install
pnpm build
pnpm link --global
dshenv --version
```

如果修改了 TypeScript 源码，需要重新执行 `pnpm build`。全局命令入口是 `dshenv`。

### 升级 dshenv

```bash
dshenv self-update --check     # 只查询：有新版本时退出码 2，已是最新时退出码 0
dshenv self-update             # 升级到 npm 上的最新版本
dshenv self-update --to 0.2.0  # 升级或回退（降级）到指定的精确版本
```

`self-update` 用 `npm view --prefer-online` 查询版本，再用安装 dshenv 的包管理器替换自身：全局 npm 安装执行 `npm install -g @costa92/dshenv@<版本> --prefer-online`，全局 pnpm 安装执行 `pnpm add -g @costa92/dshenv@<版本>`。安装过程的输出直接显示在终端（stderr），不设超时，因为中途打断可能留下装了一半的全局包。

- 不带 `--to` 时只会升级：本机版本高于 npm 上的最新版（如预发布版或本地构建）时报告 `newer-installed`，不做改动。回退必须用 `--to` 明确指定，输出会注明是降级。
- 本地链接或源码检出安装的 dshenv，以及用 pnpm 从 Git 地址安装的 dshenv，不会被替换为 npm 版本，命令以退出码 3 给出升级方法（如 `git pull && pnpm build`）。`--check` 对这类安装仍会报告，`method` 为 `null`。
- 失败时只显示错误码（如 `EACCES`、`ERR_PNPM_FETCH_401`），完整原因见上方包管理器自己的输出；`EACCES` 表示全局安装目录不可写。
- Windows 上 npm 会在 `dshenv.cmd` 运行期间覆盖它，升级成功后命令行可能多出一行批处理报错，可以忽略，用 `dshenv --version` 确认版本。

也可以手动升级：`npm install -g @costa92/dshenv@latest --prefer-online`。刚发布的版本在本机 npm 缓存过期前可能报 `notarget`，加 `--prefer-online` 即可。升级前先看 [CHANGELOG](CHANGELOG.md) 中的「变更」，例如 0.2.0 起清单不再接受 npm 来源的 `registry` 字段，lock 中的 git `commit` 必须是十六进制 commit id。

如不想安装全局命令，可以在项目目录直接运行：

```bash
node bin/dshenv.js --version
```

卸载全局 CLI：

```bash
npm uninstall -g @costa92/dshenv
# pnpm 安装的用
pnpm remove --global @costa92/dshenv
```

这只移除 `dshenv` 全局命令，不会删除 `$DSH_HOME`、Profile、已安装插件或 `envctl` 管理数据。

## 3. 选择 DSH 环境目录

DSH 主目录按以下优先级解析：

1. 全局参数 `--dsh-home <path>`
2. 环境变量 `DSH_HOME`
3. 当前用户主目录下的 `~/.dsh`

因此，默认行为是管理当前用户的 `~/.dsh`。建议在首次试用时显式设置一个独立目录：

```bash
export DSH_HOME="$HOME/code/dsh/dsh-demo"
```

也可以只对单条命令指定目录：

```bash
dshenv --dsh-home "$HOME/code/dsh/dsh-demo" status
```

相对路径会相对于当前工作目录解析为绝对路径。初始化后，主要文件位于：

```text
$DSH_HOME/
├── profiles/                 # DSH Profile 实际安装状态
└── envctl/
    ├── manifest.yaml         # 期望状态
    ├── lock.json             # 已解析的确定版本或源码
    ├── state.json            # 最近应用状态和所有权
    ├── backups/              # apply 前的管理文件快照
    └── logs/journal.jsonl    # apply 操作日志
```

## 4. 完整示例：安装 agent-teams

下面的示例把 `@nanmicoder/dsh-agent-teams@0.1.21` 声明并安装到 `web` Profile。

### 4.1 初始化

```bash
export DSH_HOME="$HOME/code/dsh/dsh-demo"
dshenv init
```

`init` 会创建空的 `manifest.yaml`、`lock.json` 和 `state.json`。它是一次性初始化命令：目标文件已经存在时会以退出码 `3` 拒绝覆盖。

### 4.2 声明插件

```bash
dshenv install @nanmicoder/dsh-agent-teams@0.1.21 --profile web
```

这里的 `install` 是声明式命令：它把插件写入清单，并不会立即修改 `web` Profile。生成的核心清单如下：

```yaml
apiVersion: dshenv/v1
profiles:
  web:
    plugins:
      agent-teams:
        package: "@nanmicoder/dsh-agent-teams"
        enabled: true
        source:
          type: npm
          version: 0.1.21
```

### 4.3 检查 DSH 运行时

如果使用本地 Harness 源码：

```bash
dshenv \
  --harness-source "$HOME/code/dsh/deepseek-harness" \
  doctor
```

### 4.4 查看计划

```bash
dshenv plan
```

首次执行通常会显示一个 `install` 操作，并返回退出码 `2`，表示存在可执行的漂移，不表示命令崩溃。

### 4.5 先进行 dry-run

```bash
dshenv \
  --harness-source "$HOME/code/dsh/deepseek-harness" \
  apply --dry-run
```

`--dry-run` 只显示计划，不获取环境写锁，也不写入状态或 Profile。

### 4.6 正式应用

```bash
dshenv \
  --harness-source "$HOME/code/dsh/deepseek-harness" \
  apply --yes
```

当前适配器会为 `install/update` 调用等价的 DSH 插件添加操作，并把解析出的 `DSH_HOME` 传给 DSH 子进程。`enable`/`disable` 按官方公开 Profile 表示改 `dsh.profile.bundles`（关闭保留 dependencies）。`configure` 写入受管 YAML 块。执行后会重新盘点实际 Profile；只有环境已经收敛，才会提交成功状态。

`apply` 结束后会分组列出哪些改动无需重启、哪些需要重启 DSH，例如：

```text
No restart needed:
  [web] install @nanmicoder/dsh-agent-teams
```

**哪些改动无需重启**：运行中的 DSH 默认开启热加载（`@deepseek-ai/dsh-hmr`），它监视 Profile `package.json` 中的 `dsh.profile.bundles` 与 `cordis.patch.yml`。因此在热加载开启的 Profile 上，`install`、`enable`、`disable`、`configure`、`remove` 当场生效，`status` 显示 `healthy`。升级已装插件（npm 版本、Git commit、本地源码变化）不改变 bundle 列表，旧模块仍留在内存中，一律需要重启。dshenv 用 `dsh --profile <p> --dump-config` 判断热加载状态：headless 等关闭热加载的 bundle、自定义了 `hmr` 行、DSH CLI 不可用或 Profile 尚未创建时，所有改动都按需要重启处理，括号内给出原因。

需要重启时，`status` 会显示 `restart-required`；重启 DSH 后运行 `dshenv mark-restarted`（可加 `--profile`；旧名 `dshenv restarted` 仍可用）确认，状态才会回到正常。

注意：

- 「无需重启」表示 DSH 会自动重新加载；dshenv 不确认插件是否真的加载成功（DSH 只在日志里记录重新加载失败），有疑问时查看 DSH 日志。
- `configure` 会列在分组里，但不写入 state，所以只含 `configure` 的 apply 之后运行 `dshenv mark-restarted` 可能显示清除了 0 个插件。
- 判定为无需重启的 `remove` 会连同该插件此前的 `restart-required` 条目一起删除（插件已经不在了）。

不带 `--yes` 的 `apply` 只预览，与 `apply --dry-run` 相同：展示计划，有变更时退出码 `2`，并在 stderr 提示加 `--yes` 重跑。没有交互确认提示；审阅计划后再运行 `apply --yes`。只想动一个 Profile 时，`plan -p web` 审阅后用 `apply -p web --yes`，其他 Profile 不受影响（skill 不属于任何 Profile，照常应用）。`rollback`、`gc`、`purge`、`adopt`、`remote add`、`remote remove`、`remote sync` 也一样：不带 `--yes` 只预览，有待执行的内容时退出码 `2`。

### 4.7 验证结果

```bash
dshenv status
dshenv plan
```

成功收敛后，`status` 显示 `healthy`，`plan` 显示没有待执行操作，两者返回退出码 `0`。

如果在仓库内使用演示目标，可以运行：

```bash
make demo-status
make demo-plan
make demo-doctor
make demo-capture
make demo-apply
```

默认工作区为 `DSH_WORKSPACE=$HOME/code/dsh`，demo 目录为 `$DSH_WORKSPACE/dsh-demo`，Harness 源码为 `$DSH_WORKSPACE/deepseek-harness`。Makefile 会自动创建工作区和 demo 目录；Harness 源码缺失时 `demo-doctor` 会明确报错，不会创建空的假仓库。可以用 `make demo-doctor DSH_WORKSPACE=/path/to/dsh`，或分别覆盖 `DEMO_HOME` / `HARNESS_SOURCE`。

其中 `demo-apply` 固定执行 dry-run。`demo-status` 已把退出码 `2` 视为“发现漂移”的正常检查结果。`demo-capture` 把候选清单打印到标准输出，不覆盖 `envctl/manifest.yaml`。

### 4.8 核对运行时是否已加载

`apply` 输出里「No restart needed」只是根据热加载推断。想确认插件真的加载了，用 `dshenv verify`：

1. 启动 `dsh web` 时，终端会打印 `dsh web: http://127.0.0.1:3080/?token=...`。把这个地址放进环境变量（不要写进脚本或提交到仓库）：

   ```bash
   export DSHENV_DSH_URL='http://127.0.0.1:3080/?token=...'
   ```

2. 运行：

   ```bash
   dshenv verify --profile web
   ```

   ```
   Runtime check for profile web (127.0.0.1:3080)
     loaded      agent-teams  @nanmicoder/dsh-agent-teams
     not-loaded  old-tool     @acme/old-tool (restart DSH, then run dshenv mark-restarted)
   Versions are not checked: DSH reports the version on disk, not the one loaded in memory.
   ```

3. 看到 `loading`（退出码 2）说明热加载还没结束，等两三秒再运行。`apply` 之后立刻运行也会看到 `loading`；若等待后仍是 `loading`，说明热加载没有生效，重启 DSH 后运行 `dshenv mark-restarted`；如果括号里是 `is waiting for services it injects`，说明插件依赖的 service 没有任何插件提供，先检查是否漏装或停用了提供它的插件，重启解决不了。带重启提示（除 `unloaded` 外任何结果都可能带上，包括升级后仍在跑旧版本的 `loaded`）时，重启 DSH 后运行 `dshenv mark-restarted`。

`dsh web` 重启后 token 会变，需要重新导出地址。报 `does not look like profile web` 时，说明地址指向的是另一个 profile 或另一个 DSH home 的 `dsh web`。

想让 dsh web 在后台一直运行，用 `dshenv web` 管理，不必占着一个终端：

```bash
dshenv web start -p web              # 后台启动并打印浏览器地址（含 token；已在运行时再次 start 会打印现有地址，web list 从不打印 token）；默认随机空闲端口
dshenv web start -p web --port 3080  # 指定端口
dshenv web list                      # 列出 dshenv 启动的 dsh web：状态、pid、地址（不含 token）；--json 可供脚本使用
dshenv verify -p web                # 没设 DSHENV_DSH_URL 时自动连这个 dsh web
dshenv web stop -p web               # 停止它以及它启动的子进程
```

- 地址与 pid 记在 `envctl/run/<profile>.json`，输出写到 `envctl/run/<profile>.log`（均为 `0600`）。已在运行时 `start` 只报告现有的那个。
- `status` 的状态：`running`；`not running`（已退出，再次 `start` 会启动新的）；`not running (leftover processes)`（dsh web 退出了，但它启动的子进程还在，`start` 或 `stop` 会先停掉它们）；`unknown`（无法确认该 pid 还是不是这次启动的 dsh web，`start`/`stop` 报错并保留记录，不停止任何进程，需要自己确认后处理）。
- `stop` 只停止 pid 与启动时间都对得上的进程；SIGKILL 后仍未退出时以非零退出码报错并保留记录，可以再执行一次。
- dsh web 与启动它的终端分离：Linux 与 macOS 上在独立进程组中运行，Windows 上不附着在启动它的控制台上，关闭终端后都继续运行。

更多说明见 README 第 24 节。

只想核对一次、不留下服务时，加 `--start` 让 dshenv 临时启动一个：

```bash
dshenv verify --profile web --start
```

它用下一节的 DSH CLI 执行 `dsh --profile web --no-open --port 0`（随机空闲端口，不打开浏览器），从输出里读出地址（不打印 token），核对完即停止它以及它启动的子进程（如 stdio MCP 服务）。`--start` 不读取 `DSHENV_DSH_URL`，也不能与 `--allow-remote` 同用；Profile 必须已存在（DSH 会自动创建不存在的 Profile，核对不应产生这种副作用）。只有带 web 应用的 Profile 能这样核对，bundles 选了 `dsh-headless`、`dsh-acp-app` 或 `dsh-sdk-app` 的 Profile 以退出码 3 报 `Profile <p> runs <应用包>, not dsh web`。60 秒内没有打印地址也会停止并报错。

## 5. DSH CLI 的解析优先级

需要调用或探测 DSH 时，`dshenv` 按以下顺序选择命令：

1. 环境变量 `DSH_CLI`
2. 命令行 `--harness-source <路径>`（相对路径按当前目录解析；目录不存在时以退出码 3 报错，不会改用后面的选项）
3. `manifest.yaml` 中的 `environment.harness.sourceDir`
4. `PATH` 中的 `dsh`

本地 Harness 源码会被转换为：

```bash
pnpm --dir /path/to/deepseek-harness dsh
```

也可以将源码目录写入清单：

```yaml
apiVersion: dshenv/v1
environment:
  harness:
    sourceDir: /absolute/path/to/deepseek-harness
    allowUntestedVersion: false
profiles: {}
```

`DSH_CLI` 可以是单个可执行文件，也可以是 JSON 字符串数组：

```bash
export DSH_CLI=/absolute/path/to/dsh

# 带固定参数时使用 JSON 数组；命令不会交给 shell 展开。
export DSH_CLI='["/absolute/path/to/runtime", "/absolute/path/to/dsh-entry.js"]'
```

不要把 Token、Authorization header 等敏感信息写入命令、清单或日志。虽然运行时探测会避免回显 `DSH_CLI` 参数，仍应优先使用环境或凭据系统提供认证。

## 6. 清单与声明式命令

### 选择 Profile（`-p`）

`-p` 是 DSH Profile 的名字（`profiles/<名字>/` 目录名，也是清单 `profiles:` 下的键）：

- 作用于单个 Profile 的命令（`install`、`update`、`enable`、`disable`、`remove`、`purge`、`plugins config`、`tools`、`verify`、`web start`、`web stop`）不写 `-p` 时取 `DSHENV_PROFILE`；两者都没有时，`verify`、`web start`、`web stop` 用清单里唯一声明的 Profile，其余命令报错并列出可选的 Profile：

  ```
  Missing -p, --profile <name>: choose one of acp, headless, sdk, web, or set DSHENV_PROFILE
  ```

- `plugins list`、`plan`、`apply`、`status`、`pull`、`capture`、`overlay show`、`mark-restarted`、`web list` 的 `-p` 只是过滤，不写表示全部 Profile，不读 `DSHENV_PROFILE`。
- `source clone|show|sync`、`new` 的 `-p` 表示把克隆或新建的包作为受管插件登记到该 Profile（`sync` 同时更新 lock commit）；不写时只处理给出的目录，不改清单。

平时只用一个 Profile 时，可以在 shell 配置里 `export DSHENV_PROFILE=web`；写入类命令用到它时会在 stderr 提示 `Using profile 'web' from DSHENV_PROFILE`，只读命令不提示。

`install`、`new -p`、`source clone -p` 指定一个清单没声明、DSH 也没创建的 Profile 时，会按拼写错误拒绝并给出相近的名字（如 `did you mean 'web'?`）；确实要新建 Profile 时加 `--new-profile`。

### `install <spec>`

向指定 Profile 的清单添加一个别名，或改写同一个包已有别名的来源（别名已指向另一个包时拒绝，用 `--as` 换别名）：

```bash
# npm，必须写精确版本（x.y.z）；不带版本、^1.0.0、latest 等会被拒绝（退出码 3）
dshenv install @nanmicoder/dsh-agent-teams@0.1.21 --profile web

# 自定义别名
dshenv install @scope/example@1.2.3 --profile web --as example

# 本地目录；写入清单时会转换为绝对路径
dshenv install /absolute/path/to/plugin --profile web

# Git URL（替换为实际仓库和固定 ref）；包名默认取 URL 末段，与仓库 package.json 不同时用 --package 指定
dshenv install 'https://github.com/example/dsh-plugin-example.git#main' --profile web --package @example/dsh-plugin

# 随 DSH 发布的 bundle（in-box），不带版本；apply 只把它加进 Profile 的 bundles
dshenv install in-box:@deepseek-ai/dsh-acp-app --profile acp
```

本地目录的包名读取其 `package.json` 的 `name`，没有时才用目录名。对已有别名再次 `install`（base 或 overlay 层）只替换来源，保留原有 patches 与启用状态。带账号密码或 token 的 git URL 会被拒绝。

npm 来源在 `install` 与 `update --to` 时先用 `npm view` 核对：包在而版本不存在时以退出码 3 报错并给出最新版本；npm 看不到这个包（可能是需要凭据的私有包）、拒绝凭据或查询不了（离线，约 5 秒超时）时只警告，照常写入。加 `--no-npm-check` 或设 `DSHENV_NPM_CHECK=off` 跳过核对。

清单和 overlay 中的 npm 版本只能是精确版本，`update --to` 同理；已有清单若写了范围会校验失败，改成实际要用的精确版本即可。`capture` 遇到只声明了范围、实际没有安装的包会跳过并给出警告。

支持的清单源码类型包括 `npm`、`git`、`local-link`、`local-file` 和 `in-box`。`in-box` 插件随 DSH 发布，只通过 Profile bundles 体现启用与否，`enabled: false` 即从 bundles 移除。改变插件的来源类型（如 npm 改为 git）时，`plan` 会给出 `update` 按新来源重装。命令行 `install` 识别 npm、Git、本地路径和 `in-box:<包名>` 四类输入；`in-box` 要求 Profile 已存在（先用 `dsh --profile <名字>` 创建一次）。

Git 计划必须在 `lock.json` 中有确定的 commit。用 `source clone --profile` 会写入 lock commit。只有清单中的分支、ref 或未锁定 commit 时，计划会显示 `blocked`。清单里的 `commit`（例如 `install <url>#<sha>` 写入的）不会被当作安装目标：lock 没有 commit 时计划提示先锁定；与 lock commit 不一致时也会 `blocked`，删掉清单里的 `commit`，或用 `source sync --profile <p> --ref <sha>` 把 lock 移过去。

### `plugins list`

```bash
dshenv plugins list
dshenv plugins list --profile web --json
```

### `update`

```bash
dshenv update agent-teams --profile web --to 0.1.22
```

只改清单（以及已有 lock）里的精确 npm 版本，不解析 latest。随后 `apply --yes` 才会真正更新。

### `plugins config`

```bash
dshenv plugins config set agent-teams taskPlanning captain --profile web
dshenv plugins config get agent-teams taskPlanning --profile web
dshenv plugins config validate agent-teams --profile web
dshenv plugins config unset agent-teams taskPlanning --profile web   # 删掉一个键
dshenv apply --yes
```

值按 JSON 解析，解析不了时当作字符串。DSH 用补丁的 `config` 整体替换插件的配置，所以清单里还没有这个插件的补丁时，`config set` 先把 DSH 当前为它组合出的全部配置抄进补丁，插件的默认值得以保留。只在没有 dshenv 补丁生效时抄（overlay 的补丁也算）；抄来的配置含本机路径时写 base 会被拒绝，改用 `--layer overlay`；抄不了时只写这个键，并在 stderr 说明原因。DSH 为插件组合出了配置而其中没有这个顶层键时，`config set` 在 stderr 提示一行并给出相近的键名，然后照常写入（DSH 只组合出带默认值的键，插件文档里的键可能不在其中）；加 `--force` 不再提示。路径为空，或含 `__proto__`、`prototype`、`constructor` 时以退出码 3 拒绝。`config unset` 在该插件的所有 patch 里找这个键，删完后空的 patch 一并删掉。

`set` 只写 manifest；`apply` 才会落到 `cordis.patch.yml` 受管块。一个插件可以声明多个 patch，每个写成一个带 digest 的受管块；`enabled: false` 的 patch 不写入，已写入的会在下次 `apply` 时移除，从清单删掉 patch 同样会清掉对应受管块。插件别名不能包含空白字符。

### `enable` 与 `disable`

```bash
dshenv enable agent-teams --profile web
dshenv disable agent-teams --profile web
dshenv apply --yes
```

这两个命令只把清单中的 `enabled` 改为 `true` 或 `false`。`apply` 按 `dsh.profile.bundles` 执行：禁用保留 `dependencies`。

### `remove`

```bash
dshenv remove agent-teams --profile web --yes
```

`remove` 只删除清单声明。若 `state.json` 的 `resources.plugin` 记着该插件的所有权，随后的 `apply --yes` 会从 `bundles` 移除并调用 `dsh plugin remove`。没有所有权记录的实际插件会显示为 `unmanaged`，不会生成删除操作。当前 `--yes` 被命令接受，但 `remove` 本身没有交互确认，也不会立刻卸载。

### `tools`

列出、开关和配置 Profile 里 DSH 的内置工具（终端、文件、网络、代码等）。状态读自 `dsh --profile <p> --dump-config`，所以 Profile 必须已存在、DSH CLI 可用（见第 5 节）：

```bash
dshenv tools list -p web                                        # 默认 agent 预设的工具：+ 开启，- 关闭，~ 按条件关闭
dshenv tools list -p web --preset ptc                           # 看另一个预设；--all 列出每个位置
dshenv tools disable tool-web -p web                            # 关闭；enable 打开（id 见 tools list）
dshenv tools config get tool-web -p web                         # 查看配置；加 <路径> 只看一个键
dshenv tools config set tool-web fetchMaxOutputChars 20000 -p web   # 设置一个键
dshenv tools config unset tool-web fetchMaxOutputChars -p web       # 删掉一个键
dshenv tools reset tool-web -p web                              # 删掉改动它的 patch，恢复 DSH 的默认
dshenv apply --yes
```

`tools config get|set|unset` 与 `plugins config` 写法相同，旧写法 `tools config <tool> [路径] [值]` 仍可使用。tools 写 base 时，若这条在清单 base 里还没有，而 DSH 当前组合出的配置已含 dshenv 补丁（如已 apply 的 overlay 写的），或含本机路径，以退出码 3 拒绝，改用 `--layer overlay`。结果写进清单的 `profiles.<profile>.patches`，`apply` 才写进 DSH。web 等 Profile 的工具在 agent 预设里，dshenv 会把当前预设整份复制进清单再改目标工具，这个预设从此固定、不再跟随 DSH 升级，`plan` 会在 `Pinned agent presets` 下列出；`tools reset <tool>` 删掉那条预设 patch（该预设内的所有工具改动一起撤销），再 `apply` 即恢复跟随。只接受 `tools list --all` 列出的 id；不在 Profile 组合里的工具不能用 `enable` 打开，需先安装对应的包。细节见 README 第 23 节。

### 当前 `apply` 支持矩阵

| 计划操作 | `apply` 是否执行 | 说明 |
| --- | --- | --- |
| `install` | 是 | 通过 DSH CLI 的插件添加操作执行 |
| `update` | 是 | 使用同一添加操作收敛到目标版本；Git 插件已装 commit 与 lock 不一致、本地来源（`local-file`/`local-link`）源码 digest 与 lock 记录不一致或尚未记录时也会触发，成功后 digest 写回 lock |
| `enable` | 是 | 把包加入 Profile `package.json` 的 `dsh.profile.bundles`，不调用 DSH CLI |
| `disable` | 是 | 从 `dsh.profile.bundles` 移除，保留 `dependencies` 中的包，不调用 DSH CLI |
| `remove` | 仅受管 | 无所有权则只标 unmanaged；有所有权则 `apply` 调用 `dsh plugin remove` |
| 配置补丁 | 是 | digest 不一致时 `configure`，写入受管 YAML 块 |

## 7. `plan`、`status` 与退出码

```bash
dshenv plan
dshenv status
dshenv --json status
```

- `plan` 展示逐项操作和未受管插件。
- `status` 汇总环境状态、Profile 数量和待执行操作数量。
- 全局参数 `--json` 可供脚本和 CI 使用。

退出码约定：

| 退出码 | 含义 |
| --- | --- |
| `0` | 命令成功；对 `plan/status` 表示没有可执行漂移 |
| `1` | 意外失败，如 Git、npm 或网络错误 |
| `2` | `plan/status/apply --dry-run` 发现 `install/update/enable/disable` 等有效漂移；不带 `--yes` 的 `apply`、`rollback`、`gc`、`purge`、`adopt`、`remote add`、`remote remove`、`remote sync` 预览有待执行的内容；`verify` 有插件仍在加载；`self-update --check` 有可安装的版本；`pull --dry-run` 有可收进的变更 |
| `3` | 用法错误（缺参数、未知选项或命令），或清单、输入、目标文件校验失败；加 `--json` 时错误以 JSON 输出 |
| `4` | DSH 能力、命令解析或操作类型不受支持 |
| `5` | 环境降级、存在 `blocked` 计划或运行时执行后未收敛 |

在 shell 脚本中应显式接受漂移退出码：

```bash
set +e
dshenv plan
code=$?
set -e

if [ "$code" -eq 0 ]; then
  echo "环境已同步"
elif [ "$code" -eq 2 ]; then
  echo "发现待应用变更"
else
  exit "$code"
fi
```

仅存在 `unmanaged` 插件时，计划没有删除操作，因此 `plan` 当前返回 `0`；请同时阅读输出中的未受管列表。

## 8. 捕获和接管现有环境

已有 DSH Profile 不需要重新安装，可以先捕获实际状态：

```bash
# 输出到终端，不修改管理文件
dshenv capture

# 只捕获 web Profile，并写入新的候选文件
dshenv capture --profile web --output ./web-candidate.yaml
```

`--output` 使用“仅创建”方式写文件，已有同名文件时拒绝覆盖。候选文件同时包含 `manifest`、`lock` 和警告，必须先人工审阅。

确认后接管：

```bash
dshenv adopt ./web-candidate.yaml               # 预览将接管的插件，退出码 2，不写文件
dshenv adopt ./web-candidate.yaml --yes
```

`adopt` 会重新盘点实际环境并检查候选是否过期，然后合并清单、锁文件和所有权记录。当实际安装版本可以读取时，候选中的 npm 版本必须与其一致；插件已经消失或可读取的版本发生变化时会拒绝接管。已有的清单、锁文件或状态文件无法读取时，`adopt` 直接报错退出（退出码 3），不会覆盖它们；清单里已声明的包沿用原有别名，不会因 capture 生成的别名不同而重复。

不带 `--yes` 时 `adopt` 只列出将接管的插件，不写任何文件；审阅后再带 `--yes` 执行。

`capture` 本身不会接管所有权，只有 `adopt` 会更新活动管理文件。

### 同步 DSH 里改的设置

在 DSH 界面里改模型、语言、权限等设置时，DSH 会改写 Profile 的 `cordis.patch.yml`。`plan` 会列出这些条目：

```text
Patch entries not in the manifest (run 'dshenv pull --yes' to manage them):
  ? [web] locale, agent-default-model, skill-filesystem
```

用 `dshenv pull --yes` 把它们收进清单（`profiles.<profile>.patches`），文件里的条目随之整理进 dshenv 的受管块：

```bash
dshenv pull          # 预览
dshenv pull --yes    # 收进清单
dshenv plan          # 应当没有变更
```

含本机绝对路径的条目（如 `skill-filesystem` 的 `customSkillDirs`）会写进本机 overlay：没有选中 overlay 时，`pull` 新建并选中 `local`。这样基础清单可以提交到仓库或经团队 remote 共享，换一台机器也不会带上本机路径。

之后两个方向都能同步：

- 在 DSH 里改了受管块里的设置，`plan` 报 `Profile patches were edited in DSH`：运行 `dshenv pull --yes` 保留 DSH 的改动，或运行 `dshenv apply --yes` 用清单覆盖。
- 在清单里改了设置：`dshenv apply --yes` 写回 DSH。
- 两边都改过时 `pull` 会拒绝，用 `--prefer dsh` 或 `--prefer manifest` 指定以哪一边为准。

`$DSH_HOME/skills` 下的 loose skill（例如 `dshenv new skill <名字> --loose` 生成的）同样由 `pull` 收进 `envctl/skills/<名字>`，`apply` 再把它复制回 DSH；被覆盖或删除的 DSH 副本移进 `envctl/trash`，可用 `dshenv gc` 清理。把 `envctl/skills` 提交到团队配置仓库后，技能会随 `dshenv remote sync` 同步。

`plan` 在 `Unmanaged plugins (not in manifest; run 'dshenv pull --yes' to manage them)` 下列出的插件同样由 `pull` 接管：npm、git、in-box 插件写进基础清单，`local-link`/`local-file` 插件写进本机 overlay（规则与含本机路径的条目相同），lock 与所有权一并记录，接管后 `plan` 不再列出它们。以前需要 `install <path> --layer overlay` 再 `disable` 才能收进 overlay 的本地链接插件，现在一次 `pull --yes` 即可。

`adopt` 接管 Profile 时会自动做一次 `pull`（包括 loose skill，不包括候选文件之外的插件）。

## 9. 管理本地和 Git 源码

`source clone --profile` 会把仓库放到 `envctl/sources/<profile>/<package>`（包名取仓库 `package.json`，可用 `--package` 指定），并写入 lock commit，随后 `plan`/`apply` 才能安装。清单里这个别名已声明同一仓库的 `commit` 或 `ref`（如 `install <url>#<sha>` 写入的）时，克隆并锁定它而不是 HEAD，commit 不在仓库里时报错；给了 `--ref` 时改用该 ref 并写进清单。别名默认与 `install` 相同（仓库名去掉 `dsh-plugin-`、`dsh-` 前缀）；别名已指向另一个包时拒绝（退出码 3）。任一步失败时本次克隆会被清除。不带 `--profile` 时仍可克隆到任意目录，但 `purge` 不会删除外部目录。

```bash
dshenv source clone https://example.invalid/plugin.git --profile web --as demo
dshenv source sync --profile web --as demo --ref origin/main
dshenv source show --profile web --as demo
dshenv source clone https://example.invalid/plugin.git /absolute/path/to/plugin --ref main
```

`source sync` 遇到未提交改动会拒绝更新，对 `envctl` 之外的检出只快进（`--ref` 指向更旧的 commit 时拒绝）。带 `--profile` 时还会把 lock 里的 commit 更新为新 HEAD；受管 clone 可以用 `--ref` 退回到更旧的 commit，detached HEAD 不给 `--ref` 时跟随清单的 `ref` 或远端默认分支。

## 10. 使用 `doctor` 排查运行时

```bash
dshenv doctor
dshenv --json doctor
dshenv \
  --harness-source "$HOME/code/dsh/deepseek-harness" \
  doctor
```

`doctor` 会检查 DSH 版本、运行时发现能力、官方操作表面证据以及管理文件是否存在。

能力矩阵中的 `mutations=false` 或 `runtime.mutationsSupported=false` 表示通用、完整的环境写能力仍未开放；它不等于 `apply` 命令不存在。当前 `apply` 是一条范围更窄的 DSH CLI 适配路径：插件 `install/update/remove` 调用 DSH CLI，`enable/disable/configure` 改写 Profile 文件。

`doctor` 默认拒绝未经验证的 DSH 版本。确需试验时可显式放行：

```bash
dshenv --allow-untested-dsh doctor
```

这只绕过 `doctor` 的版本白名单。`apply` 在调用 DSH CLI（`install/update/remove`）前会 probe `--version`，使用与 `doctor` 相同的兼容矩阵；`--allow-untested-dsh` 与清单中的 `environment.harness.allowUntestedVersion: true` 对两者同样生效。`enable/disable/configure` 不要求 DSH CLI。

## 11. 卸载、清理与 purge

当前需要区分三件事：

1. 卸载 `dshenv` CLI：使用 `npm uninstall -g @costa92/dshenv`（pnpm 安装的用 `pnpm remove --global @costa92/dshenv`）。
2. 从清单移除插件：使用 `dshenv remove <alias> --profile <name>`。
3. 从 DSH Profile 卸载受管插件：在上一步之后运行 `dshenv apply --yes`。没有所有权记录的插件会变成 `unmanaged`，需要用官方方式处理。

`dshenv rollback --yes` 恢复 `envctl` 下的管理文件：`manifest.yaml` / `lock.json` / `state.json`、`envctl/skills`、`remote.json`，以及快照时保存的 overlay（团队 overlay、`pull`/`sync` 改写的本机 overlay、`apply` 时生效的 overlay）。不带 id 时跳过失败的 `apply` 留下的快照（它们已经自己恢复过），恢复到最近一次真正改动过文件的操作之前，输出写明跳过了哪些。它不会卸载或重装 Profile 里的包；由 `apply` 安装、仍装在 Profile 里的插件保留所有权记录，之后从清单删除时照常卸载。恢复前把当前文件另存为新快照（输出中给出 id，可再 rollback 回去）。`dshenv purge <plugin> --profile <name> --yes` 把有所有权的受管 patch 复制进 `envctl/trash` 并去掉 live 受管块；`envctl/sources` 下的受管克隆一并移入 trash，但有未提交改动时拒绝执行（`--dry-run` 同样报错），先提交或移走改动。`apply` 删除插件后所有权记录随之去掉，这时用包名执行 `purge` 仍可清理它留在 `envctl/sources` 下的 clone（清单不再声明该包时）。`dshenv gc --yes` 删除 `envctl/trash` 中超过 `--older-than`（默认 7 天）的条目，以及 `envctl/backups` 中超过同一期限的快照，但始终保留最近 10 个快照（`rollback` 只能回到还在的快照）。不要为了重新初始化而直接删除整个 `$DSH_HOME`。

## 12. 安全注意事项

- 在任何真实变更前先执行 `plan` 和 `apply --dry-run`。
- `apply` 会获取 `$DSH_HOME/envctl/dshenv.lock` 独占锁，并在 `envctl/backups/` 备份当时的管理文件（`manifest.yaml`、`lock.json`、`state.json`、`envctl/skills` 等）。
- 失败时只恢复 `apply` 自己会写的 `lock.json` 与 `state.json`（快照中原本不存在的会被删除），`manifest.yaml`、overlay 与 `envctl/skills` 保持原样，apply 期间对它们的手工修改不会丢；并撤销本工具对 Profile `dsh.profile.bundles` 与 `cordis.patch.yml` 的改动。DSH CLI 已经完成的包安装、更新或卸载不会撤销，其中成功安装的插件仍记入所有权，之后从清单删除时照常卸载。恢复本身失败时，错误信息末尾会提示运行 `dshenv rollback <id> --yes`。某一步失败时，错误信息写明是哪一步（Profile、操作、别名、第几步），并提示两条路：修正清单后重新 apply，或用 `dshenv rollback <上次成功的 apply id> --yes` 回到上次成功应用的清单。失败后必须重新运行 `status` 和 `plan`。
- 按 Ctrl-C（或发送 `SIGTERM`/`SIGHUP`）中断 `apply` 时，dshenv 先结束正在运行的 DSH 插件命令，按上面的失败路径回滚，释放 `dshenv.lock` 和被结束的 DSH 留下的 `profiles/<p>/package.json.lock`，然后退出（Ctrl-C 为退出码 130）；journal 中记为 `apply-rollback`，原因是 `Apply was interrupted`。回滚期间再按一次 Ctrl-C 会立即退出，跳过剩余回滚。
- `kill -9`、断电或上面的二次 Ctrl-C 会跳过这些清理。之后 `dshenv.lock` 在持有进程已退出时会被自动接管，但 `profiles/<p>/package.json.lock` 按与 DSH 相同的约定不会自动接管：DSH 与 dshenv 会一直等待，最后报 `Timed out waiting for the profile lock`。确认没有 DSH 进程或 `dsh plugin` 命令在写该 Profile（锁文件内容是持有者的 pid，可用 `ps -p <pid>` 核对）后手工删除这个锁文件，再运行 `dshenv plan` 查看残留状态，必要时 `dshenv rollback <id> --yes`。
- `journal.jsonl` 记录操作开始、完成或回滚事件，但不是完整的 Profile 文件备份。
- 未在清单中的插件被视为 `unmanaged`，不会被静默删除。
- 本地链接和本地文件路径必须是绝对路径；只使用可信源码目录和规范的 npm 包名。
- Profile 名（清单、overlay、lock 与 `-p`）只能含字母、数字、`.`、`_`、`-`，不能以 `-` 开头，也不能是 `.` 或 `..`；Git 地址与 ref 不能以 `-` 开头，清单中的 `commit` 必须是 7-64 位十六进制 commit id。
- Git 更新要求工作区干净，并只执行 fast-forward 合并。
- `lock.json` 是确定性输入；不要随意删除或伪造 Git commit、npm 解析版本。
- 不要在清单、锁文件、patch 配置、源码 `package.json`、终端命令或操作日志中保存明文密钥。`source show --json` 会输出源码包摘要，调用前应检查其中是否包含敏感字段。

## 13. 多机器 overlay

同一份清单要在多台机器上跑，但个别机器需要不同插件开关或版本时，用 overlay 在 base 清单（`envctl/manifest.yaml`）之上按机器叠加差异，而不必维护多份完整清单。

### 文件布局与同步范围

| 文件 | 作用 | 是否跨机器同步 |
| --- | --- | --- |
| `envctl/manifest.yaml` | base 清单，格式不变 | 是 |
| `envctl/overlays/<name>.yaml` | 命名 overlay | 是 |
| `envctl/overlay-selection.json` | 本机当前选择 | 否 |
| `envctl/lock.json` | 合并结果的锁，单份 | 否（订阅团队 remote 时，团队 lock 中的条目来自远程，见第 14 节） |
| `envctl/state.json` | 本机状态 | 否 |

overlay 名只允许 `[A-Za-z0-9._-]+`。

新建 overlay 用 `dshenv overlay create <name>`（生成只含 `apiVersion` 与注释示例的 `envctl/overlays/<name>.yaml`，文件已存在时退出码 3），再执行 `dshenv overlay use <name>`；`install` 等写入命令不会自动创建 overlay 文件。例外是 `pull`：遇到含本机路径的条目而没有选中 overlay 时，它会新建并选中 `local`（见第 8 节）。

### overlay 格式示例

```yaml
apiVersion: dshenv-overlay/v1
environment:
  harness:
    sourceDir: /srv/dsh/deepseek-harness
profiles:
  web:
    plugins:
      agent-teams:            # base 已有：按字段覆盖
        enabled: false
        patches:
          - id: agent-teams
            config: { taskPlanning: solo }
      heavy-indexer:
        remove: true          # 合并结果中删除该 base 插件
      laptop-only:            # base 没有：新增，必须写全 package 与 source
        package: "@me/laptop-tool"
        source: { type: npm, version: "1.2.0" }
```

### 合并规则摘要

- 按 Profile、Profile 内按插件别名合并；base 没有的别名为新增，必须同时写 `package` 与 `source`。
- `enabled` 替换；`source` 整体替换（不做字段级合并）；`remove: true` 删除该 base 插件。
- `patches` 按 `id` 合并，同 id 的 `config` 深度合并，`enabled` 替换；base 没有的 id 追加在后。
- `environment` 对象深度合并。
- 每个合并后的插件记录出处（`origin`）：`base`、`overlay:<name>`（overlay 新增）或 `base+overlay:<name>`（被覆盖）。

### `overlay use` / `list` / `show`

```bash
dshenv overlay create laptop   # 新建空 overlay
dshenv overlay use laptop      # 本机持久选择，写入 overlay-selection.json
dshenv overlay use --none      # 清除选择
dshenv overlay list            # 列出 overlays/ 下所有 overlay，标出当前生效项
dshenv overlay show            # 合并后的清单与每个插件的出处
dshenv overlay show --json
```

选中的 overlay 优先级从高到低：`--overlay <name>` 或 `--no-overlay`（两者同时使用时报错，退出码 3）> 环境变量 `DSHENV_OVERLAY` > `overlay-selection.json`。选中的 overlay 文件不存在或校验失败时报错（退出码 3），绝不会退回只用 base。

### `--layer` 规则

有生效 overlay 时，改清单的命令（`install`、`update --to`、`enable`、`disable`、`remove`、`plugins config set/unset`、`tools enable/disable/config/reset`、`source clone --profile`、`new -p`）必须显式加 `--layer base` 或 `--layer overlay`（或设环境变量 `DSHENV_LAYER` 作为默认，它只在有生效 overlay 时起作用；没有 overlay 时 `DSHENV_LAYER=overlay` 与 `--layer overlay` 一样被拒绝），否则退出码 3。`--layer base` 写的值若被 overlay 覆盖，会在 stderr 提示这台机器上实际没变。`--layer overlay` 只把最小覆盖项写入当前 overlay 文件；`adopt` 自己决定写到哪一层：共享插件写 base，`link:`、`file:` 等本机路径的插件写进 overlay（没有生效 overlay 时新建并选中 `local`），不需要 `--layer`（传 `--layer overlay` 会被拒绝）。

### 切换 overlay 前先 `plan`

切换 overlay 会改变合并后的清单，原来受管但不再出现在新合并清单中的插件，会在下一次 `apply --yes` 时被卸载。切换后务必先跑 `plan` 或 `apply --dry-run` 确认影响，再决定是否 `apply --yes`。`plan`/`apply` 在当前 overlay 与上次 apply 记录的 `appliedOverlay` 不同时，会输出 `overlay changed since last apply: <old> → <new>`，注意这条提示。

## 14. 团队共享配置

团队希望所有成员使用同一套插件基线，同时允许每台机器做少量个性化时，把 base 清单、lock 与团队 overlay 放进一个 Git 配置仓库，成员用 `dshenv remote add` 订阅、`dshenv remote sync` 接受更新。

### 团队仓库布局

默认读取仓库内 `envctl/` 目录（`remote add --path <dir>` 可改，`.` 表示仓库根）：

| 仓库内文件 | 是否采用 |
| --- | --- |
| `envctl/manifest.yaml` | 必需，不得使用 `local-link` / `local-file` 源或本机 Git 地址，不得设置 `environment.harness.sourceDir` / `environment.sourceRoot`，插件 patch 与 profile patch 不得含 JavaScript 表达式（`__jsExpr`） |
| `envctl/lock.json` | 可选，不得包含 `local-link` / `local-file` 源条目或本机 Git 地址 |
| `envctl/overlays/*.yaml` | 可选，只取这一层，限制同 `manifest.yaml` |
| `envctl/skills/<名字>/...` | 可选，团队 skill，随 `apply` 装进 `DSH_HOME/skills`；不得含软链接或子模块 |
| 其他文件（`state.json`、`overlay-selection.json`、`backups/`、`sources/`、直接放在 `skills/` 下的文件等） | 忽略 |

仓库 URL 不得内嵌账号或 token，认证交给 SSH 或 git credential helper。

### 订阅

```bash
dshenv remote add git@github.com:team/dsh-config.git        # 只预览，退出码 2
dshenv remote add git@github.com:team/dsh-config.git --ref <commit> --yes  # 接受预览过的 commit（预览末尾给出这条命令）
dshenv remote show
```

预览会列出将写入的文件、将加入的团队 lock 条目（`<profile>/<alias>`），以及用新清单与合并后的 lock 对本机当前 Profile 计算出的 plan。接受后，`envctl/manifest.yaml` 与团队 overlay 和远程固定 commit 的内容逐字节一致；`lock.json` 中团队 lock 的条目与远程一致，本机原有的其他条目保留。订阅信息（含每个文件与每个团队 lock 条目的摘要）记录在 `envctl/remote.json`，克隆放在 `envctl/remote/repo.git`。本机已有 `manifest.yaml`、同名 overlay，或本机 lock 已有团队 lock 同名条目时需要加 `--replace`，覆盖前会先建快照。

订阅后不会自动安装任何插件，照常执行 `dshenv plan`，确认后再 `dshenv apply --yes`。

### 本机定制

远程内容是只读的：`install`、`update`、`enable`、`disable`、`remove`、`plugins config set`、`adopt` 写 base 时，写团队 overlay 时，以及 `source clone --profile`、`source sync --profile`、按 lock 固定版本的 `update` 要改写团队 lock 中的条目时，都会以退出码 3 拒绝。个性化写进本地 overlay：

```bash
printf 'apiVersion: dshenv-overlay/v1\n' > "$DSH_HOME/envctl/overlays/laptop.yaml"
dshenv overlay use laptop
dshenv disable heavy-indexer -p web --layer overlay
```

本地 overlay 不能与团队 overlay 同名。

`lock.json` 按条目归属：团队 lock 里有的 `profile/alias` 条目归远程，由 `sync` 更新；其余条目归本机。因此本地 overlay 照常可以加 Git 插件并用 `source clone --profile --layer overlay` 固定 commit，也照常可以加本地源插件，由 `apply` 记录源目录摘要，这些本机条目在 `sync` 时原样保留，也不会被当作本地改动。例外：本地 overlay 不能把团队 lock 已固定的插件改成 `local-link` / `local-file` 源，否则 `apply` 以退出码 3 拒绝（写入本机条目会覆盖团队条目）；做法是在本地 overlay 中用 `remove: true` 停用该插件，再以新的 alias 加入本地源插件。团队 lock 不允许包含 `local-link` / `local-file` 源（本机路径与摘要无法跨机器共享）。

### 接受更新

```bash
dshenv remote sync            # 拉取并预览：文件增删改与接受后的 plan，退出码 2；已是最新时退出码 0
dshenv remote sync --ref <commit> --yes   # 接受预览过的 commit，退出码 0（预览末尾给出这条命令；不带 --ref 时接受当时分支的最新 commit）
dshenv remote sync --ref v1.4.0 --yes   # 移动到订阅分支上的 tag 或 commit
```

顶层的 `dshenv sync` 是 `remote sync` 的旧名，仍可使用；下文单写的 `sync` 都指 `remote sync`。

- 只接受 fast-forward：团队改写了已发布的历史，或 `--ref` 指向旧提交、指向订阅分支以外的提交时，`sync` 拒绝（退出码 3）。
- 团队删除的 overlay 会从本机删除；本地 overlay 保持不变。当前生效的 overlay 被团队删除，或本地生效 overlay 无法与新 base 合并时，`sync` 拒绝，先调整 overlay 再同步。
- 预览按「文件」与「lock 条目」两部分列出增删改；团队删除的 lock 条目会从本机 lock 删除，本机条目不受影响。
- 本机手工改过远程文件或团队 lock 条目时，`sync` 拒绝并列出它们；把改动移到本地 overlay 后再同步，或用 `dshenv remote sync --discard-local-changes --yes` 恢复为远程内容。`dshenv remote show` 与 `dshenv doctor` 都会标出被改或被删的远程文件与条目。本机 `lock.json` 无法解析时 `sync` 一律拒绝（它可能含本机条目），请先手工修好。
- 团队仓库新增了与本机现有 overlay 同名的 overlay，或团队 lock 新增了本机 lock 已有的条目时，`sync` 拒绝，先把本机文件或条目移开。

### 回滚与取消订阅

每次接受前都会建快照，接受时输出 `Accepted <commit> (snapshot <快照 id>)`。`dshenv rollback --yes` 只恢复最近的一个快照（失败的 apply 留下的快照除外）：如果同步之后又执行过 `apply`，最近的是那次 apply 的快照：它恢复那次 apply 应用的清单，以及它运行前的 `lock.json`、`state.json`，订阅信息和同步写入的文件不变，清单在那次 apply 之前的改动也不会撤销。要撤销同步，用 `dshenv rollback <快照 id> --yes`（也可以写 `sync-<id>`），然后再 `dshenv apply --yes` 让已安装的插件跟上。撤销后固定 commit 回到旧值，之后的 `sync` 仍是 fast-forward。回滚到早于某次 `remote add --replace` 的快照时，被那次 add 覆盖的本地 overlay 恢复为原内容；那次 add 新建的远程 overlay 被删除。如果某次接受在中途被打断（例如进程被杀），下次 `sync` 会以退出码 3 提示先运行 `dshenv rollback sync-<id> --yes`，回滚后再同步。

`dshenv remote remove --yes` 取消订阅：删除 `envctl/remote.json` 与克隆，文件保留下来成为本地文件，此后可以照常写入。不带 `--yes` 时只预览，退出码 2。

### 安全含义

接受一次更新，就等于同意在本机执行该 commit 声明的所有插件。请只订阅可信的仓库，在 `--yes` 之前阅读预览中的 plan，并在 `apply --yes` 前再跑一次 `dshenv plan`。dshenv 不校验 commit 签名，信任来自固定 commit 与显式接受。

## 15. 在 CI 中使用 dshenv

`docs/examples/github-actions/dshenv-check.yml` 是一份可直接复制的 GitHub Actions 示例，适用于把 `envctl/manifest.yaml` 和 `envctl/overlays/*.yaml` 放在仓库根目录的配置仓库。示例从 npm 安装 `DSHENV_VERSION` 指定的已发布版本（`validate` 用 `npm install -g`，`drift` 用 `npx`，不改动 self-hosted runner 的全局包），升级前先读 CHANGELOG 再改这个版本号。

- `validate`：每次 push 和 PR 运行，不需要安装 DSH。把检出的仓库当作 `DSH_HOME`，先 `list --no-overlay` 校验 base 清单，再对每个 overlay 执行 `overlay show --overlay <name>`，确认都能与 base 合并；任一失败（退出码 `3`）即失败。
- `drift`：定时或手动触发，运行在装有真实 DSH 环境、带 `dsh` 标签的 self-hosted runner 上，执行 `dshenv plan`：`0` 通过，`2` 视为漂移并失败（输出计划），其他退出码按错误处理。

`plan`、`status` 在没有 Profile 的机器上会把所有插件判为未安装（退出码 `2`），因此漂移门禁只应放在真实环境所在的机器上。

## 16. 容器中运行 DSH

`docs/examples/container/` 提供一份 `Dockerfile` + `compose.yaml`，构建期在镜像内执行 `dshenv apply --yes` 装好清单声明的插件，容器启动后运行 `dsh web`：

```bash
docker build --build-context dshenv=/path/to/dshenv -t my-dsh .
docker network create dsh-net
docker run --rm --network dsh-net -p 127.0.0.1:3080:3080 -e DEEPSEEK_API_KEY my-dsh
```

`--build-context dshenv=...` 必须指向一份 dshenv 源码检出，构建阶段会从中打包安装，因此可以使用未发布的改动；只用已发布版本时检出对应的 tag（如 `v0.9.0`），不要直接用 `master`。

**安全**：容器内 `cordis.patch.yml` 把 webserver 的 `host` 设为 `0.0.0.0`，这只是为了让 Docker 能把端口转发进容器；宿主机端口发布必须限定在 `127.0.0.1:3080:3080`。DSH Web 能执行 shell 命令，改成 `3080:3080` 或用 `docker run -P` 会把远程代码执行能力暴露到局域网。回环发布只挡住局域网：同一 Docker 网络内的其他容器仍能访问 `<容器 IP>:3080` 并通过 Host 校验，此时只剩每次启动生成的 token 一道防线；直接 `docker run` 时默认 bridge 上的所有容器都在此列，所以要像上面一样放到独立网络（compose 的项目网络即可，但同项目新增的服务也能访问）。`DEEPSEEK_API_KEY` 只能作为运行时环境变量提供，不要写进镜像或构建参数。

改动 `envctl/manifest.yaml`（或 overlay）后必须重新构建镜像；不要在运行中的容器里执行 `dshenv apply`，容器不持久化 envctl 状态。完整用法、构建参数与数据卷说明见 `docs/examples/container/README.md`。

## 17. 快速开发 DSH 组件

`dshenv new <skill|agent|tool|mcp> <name>` 从模板生成组件包，跳过手写 `package.json` 与 `dsh.bundle` 配置。

| 类型 | 生成形态 | 说明 |
| :--- | :--- | :--- |
| `skill` | bundle 插件，额外一行 `dsh-skill-filesystem` 挂载自身 `skills/` 目录 | `--loose` 改为直接写 `$DSH_HOME/skills/<name>/SKILL.md`，由 DSH 自动发现；之后可用 `dshenv pull` 收进 `envctl/skills` |
| `agent` | `dsh-agent-preset` + `dsh-persona` | 供 `dsh web` 使用；工具行需自行补充 |
| `tool` | 纯 JS `defineTool` 插件 | peer 依赖 `@deepseek-ai/dsh-tools` 从运行中的 DSH 解析，无需额外安装；`--typescript` 生成 TS 版本，需先 `pnpm install && pnpm build` 再使用 |
| `mcp` | `dsh-mcp-client` | 默认 streamable-http，stdio 配置在注释中给出 |

模板要求 DSH `0.1.7` 及以上（更早版本缺少 agent 预设与 linked-package peer 解析）。

开发循环：

```bash
dshenv new tool echo-text -p web
dshenv plan
dshenv apply --yes
# 首次安装在热加载开启时无需重启；之后改源码触发的 update 会输出 Restart DSH to load:
# 此时重启 DSH 进程，再确认
dshenv mark-restarted
```

`-p` 会在生成后执行 `dshenv install <目录> -p <profile>`，但不会自动 `apply`；后续修改本地包源码会改变其 digest，下一次 `plan` 即可发现变化并触发 `update`。

## 18. 常见错误排查

### `Target file already exists`

原因：对已经初始化的目录再次执行了 `init`，或者 `capture --output` 指向已有文件。

处理：继续使用现有环境，先运行：

```bash
dshenv status
dshenv plan
```

需要全新演示环境时，改用新的 `DSH_HOME`，不要直接覆盖原管理文件：

```bash
DSH_HOME="$HOME/code/dsh/dsh-demo-2" dshenv init
```

### `make` 把退出码 `2` 显示为错误

直接执行 `dshenv plan/status` 时，退出码 `2` 表示发现漂移。当前 `make demo-status` 只接受退出码 `0/2`；`demo-plan` 使用 Make 的忽略错误前缀，会忽略包括校验或降级错误在内的所有非零退出码，因此排错和 CI 应直接运行 `dshenv plan` 并检查退出码。

### `DSH CLI was not found`

确认下列方式至少有一种可用：

```bash
dshenv --harness-source /absolute/path/to/deepseek-harness doctor

export DSH_CLI=/absolute/path/to/dsh
dshenv doctor

command -v dsh
```

### `Git source has no locked commit`

Git 源缺少 `lock.json` 中的确定 commit。不要让工具猜测 HEAD；先固定来源，并通过 `capture`/`adopt` 形成可验证的锁记录。若提示 `declares commit ... in the manifest`，说明清单写了 `commit` 但 lock 没有或与之不同，见上文 Git 来源说明。

### `Apply execution finished but the environment still has pending operations`

DSH 子命令返回成功，但重新盘点仍发现漂移。查看 Profile 的 `package.json`、DSH 输出和：

```bash
dshenv status
dshenv plan
tail -n 20 "$DSH_HOME/envctl/logs/journal.jsonl"
```

该情况返回退出码 `5`，不会提交新的成功状态。

### `Timed out waiting for the profile lock`

dshenv 改写 Profile `package.json` 或 `cordis.patch.yml` 前会获取 DSH 的 `package.json.lock`，最多等 30 秒。超时说明有 DSH 进程或 `dsh plugin` 命令正在写该 Profile，或某个进程异常退出后留下了锁（DSH 与 dshenv 都不会接管已退出进程留下的锁，只能手动删除）。本次 `apply` 会自动回滚，但回滚本身写 bundle 与 `cordis.patch.yml` 时也可能要等这把锁；回滚未能完成时运行 `dshenv plan` 查看现状。DSH Web 安装插件时整个安装过程都持锁，可能超过 dshenv 的 30 秒等待，等安装结束后再重试。确认没有 DSH 或 `dsh plugin` 正在写该 Profile 后，删除报错中给出的锁文件再重试。

### `Environment lock is already held`

锁被占用时工具会以 5–40ms 的随机退避间隔重试，最多等 5 秒，仍拿不到才报此错。另一个 `apply` / `rollback` / `purge` / `gc` 可能仍在运行。先确认对应进程是否存在；不要在活动操作期间手工删除锁文件。对同一主机上已经退出的进程，以及超过 5 秒仍为空或无法解析的锁文件，工具会识别并接管陈旧锁；接管经 `dshenv.lock.reclaim` 目录串行化，同一时刻只有一个等待方能接管。若错误信息提示存在陈旧的 reclaim 标记（接管过程中进程崩溃所致），确认没有 dshenv 进程运行后手工删除该目录。

### `source sync` 拒绝脏工作区

先在目标仓库提交或暂存本地修改，再重新执行。工具不会自动丢弃未提交内容。

## 19. 获取命令帮助

```bash
dshenv --help
dshenv apply --help
dshenv source --help
```

需要供脚本消费时，把全局 `--json` 放在子命令前：

```bash
dshenv --json status
```
